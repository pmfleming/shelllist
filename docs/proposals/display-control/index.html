01 / THE DECISION

One surface. Two depths. One display owner.

RECOMMENDED

A compact Displays callout that expands into a layout workspace.

Move both Laptop & external display and Display layout out of Power & sleep. Keep their existing daemon integration and recovery guarantees.

  1. Open: a dedicated bar control, the existing Displays shortcut, or shelllist open displays.
  2. Glance: active screens, current arrangement and the saved external-display preference.
  3. Edit: select a monitor, arrange visually or with keys, then Preview → Keep.
  4. Recover: the daemon, not the popover, owns rollback and laptop fallback.

Move

Monitor behavior

External-display preference, connected outputs, resolution, refresh rate, scale, rotation, enablement and layout.

Leave in Power

Sleep behavior

Lid action, idle timeouts, sleep/hibernate, battery care and power profiles. Add a small “Display settings →” migration link; do not duplicate the controls.

Keep out of v1

Unrelated complexity

No new DDC brightness stack, HDR/VRR controls, workspace assignment UI or named profile engine. Mirror/presentation modes need backend work first.

Important distinction: “Prefer external displays” is a persistent docking policy, not an “external only right now” preset. Name and present it accordingly. Layout edits are drafts; the policy toggle saves immediately after acknowledgement.
What the current code already does — and what actually needs moving
  • battery/PowerControlsPane.qml contains BatteryDisplayPane and BatteryLayoutPane. The latter is a connector-by-connector form, with numeric X/Y rather than a visual arrangement.
  • shell/SurfaceRegistry.qml::openDisplays() loads battery and selects its power tab. There is a Displays command/shortcut, but no independent Displays surface descriptor.
  • BatteryController, BatteryBackend, BatteryApi.js and BatteryFlow.js own display state and requests. That ownership should become display-specific, not remain coupled to battery action state.
  • bar-daemon already supplies displayPolicy.set, displayLayout.preview/confirm/revert and display-policy.changed. A preview is journalled, normally reverts after 20 seconds, and is recovered on restart/resume. Reconciliation runs at two-second intervals; rollback may take longer if the compositor is unavailable.
  • Layout previews keep the internal panel enabled as a fallback. Its eventual enablement belongs to docking policy. The new UI must distinguish actual output state from that safety-constrained preview draft.

Inspected local worktrees: Shelllist a0bf53b, bar-daemon 334c997. The existing integration is opt-in via programs.shelllist.displays.enable. No hardware, docking or output changes were performed for this review.

Common best practice

See what will change

Numbered screens, friendly names plus connector IDs, logical-size geometry, and a clear selected output. Hide precision fields until needed.

Keyboard-first best practice

No pointer-only operations

Reach every control with keys. Offer spatial movement, explicit preview and safe confirmation. Never overload typing in a field with global letter shortcuts.

Safety best practice

One authoritative owner

UI closure, a dead client, failed apply or hotplug must not turn a draft into a permanent unusable configuration. State is confirmed from the compositor.

03 / THREE INTERFACE STUDIES

Three possible front doors.

Original static mockups, not screenshots of running software. Sample hardware and state are illustrative. Dark colors stand in for Shelllist theme tokens; use the user’s actual palette in implementation. The pictures are embedded SVGs, so this HTML works offline without fonts, scripts or image downloads.

A / Compact Displays callout

The everyday default: connected screens, a readable arrangement, the persistent docking preference, and one obvious route into editing.

Recommended default
Why choose it

Best match for the existing Shelllist callout vocabulary. Low cognitive load and a clear destination independent of battery hardware.

Trade-off

Detailed arrangement takes one more action. A tiny map is a summary, not a drag target.

Keyboard path

Displays shortcut → Arrange & configure → Enter. Policy is an explicitly labelled switch, not an ambiguous mode cycle.

B / Canvas-first workspace

Open directly into the visual layout and per-screen inspector. Strong for multi-monitor setup; heavier for simply checking dock state.

Recommended expansion for A
Why choose it

Fastest for arrangement, rotation and mixed-DPI work. Supports three or more outputs with pan/fit and a stable selected-screen inspector.

Trade-off

Too much UI for the common “is my external screen active?” question. Must collapse gracefully on small laptop viewports.

Keyboard path

Select screen → move with arrows → Ctrl+Enter to preview → explicitly focus Keep. Numeric fields remain available for precise placement.

C / Command-first palette

Search actions and screens using Shelllist’s provider model. The right pane previews context; complex editing still opens the visual editor.

Optional later entry point
Why choose it

Excellent for frequent keyboard use; actions such as “identify” or a monitor name are directly searchable.

Trade-off

Less discoverable for occasional use. Geometry is a poor fit for a list of commands alone.

Keyboard path

Type a screen/action → arrows → Enter. Reuse the same controller, capability checks and trial flow as the callout.

04 / INTERACTION CONTRACT

Fast to reach. Deliberate to change.

Entry & presentation

  • Add a monitor glyph near brightness in the bar; keep brightness wheel/click behavior unchanged. No wheel-to-change-layout behavior.
  • Show the display control on laptop-only and desktop systems, not only while an external monitor is attached. Compact it to a glyph at narrow widths; retain the shortcut and surface chooser route.
  • Left click opens A using the shared popover host. Preserve the existing documented Super+P route; verify its host binding at deployment. Do not add a conflicting second global binding.
  • “Arrange & configure” expands the same surface toward B. Clamp to available logical screen space; stack inspector below canvas on narrow outputs.
  • Open on the invoking/focused output. If that output disappears, move the trial UI to a surviving usable screen rather than leaving it on an orphaned host.

Layout & output details

  • Number every connected screen; Identify briefly shows the same number and connector on each enabled output. Disabled outputs stay listed, but are not woken for identification.
  • Render desktop geometry after scale and rotation, not panel millimetres or raw pixel resolution. Preserve logical adjacency, negative coordinates and aspect ratio.
  • Offer edge snapping, fit-to-view and explicit left/right/above/below placement as accessible alternatives to dragging.
  • Resolution and refresh are separate controls in the UI but resolve to one advertised backend mode. Preserve exact mode values; never invent a “60 Hz” mode from rounding.
  • Retain custom valid scale values; offer validated presets. Keep advanced reflection and X/Y fields reachable. Internal-panel enablement explains its policy ownership instead of exposing an ineffective checkbox.

01 / DRAFT

Edit safely

Snapshot current outputs. Local edits do not alter the desktop. Preserve focus and input across telemetry updates.

02 / PREFLIGHT

Validate again

Check capabilities, finite values, topology and at least one usable output. Reject stale drafts; do not silently adapt a dangerous plan.

03 / TRIAL

Preview for 20 s

Daemon journals then applies. UI disables conflicting edits. Initial focus is Revert, not Keep.

04 / FINISH

Keep or recover

Keep requires the live trial ID and observed configuration. Timeout, cancel or lost UI do not commit the layout.

ContextKeyboard contract
Callout / inspectorTab/Shift+Tab move focus; arrows operate the focused control; Enter/Space activate it. No global single-letter shortcuts while typing.
Arrangement canvasOne tab stop enters a composite screen selector. [/] select previous/next output. Arrows move the selected draft by 16 logical px; Shift makes 1 px, Ctrl makes 64 px. Optional h/j/k/l aliases apply only here. The next Tab exits the canvas.
Draft editorCtrl+Enter previews only if valid and dirty. Escape first cancels an active control/drag; otherwise asks to discard a dirty draft. It never silently applies edits.
Active trialEsc requests Revert. Enter activates the focused button; initial focus is Revert. Ignore the held key/repeat that opened the trial so it cannot immediately Keep or Revert. Closing requests revert; if unreachable, daemon timeout remains authoritative.

Use visible focus rings, screen numbers and text labels in addition to color. Expose canvas selection, logical position and control names to accessibility APIs; provide relation buttons/numeric fields for non-spatial navigation. Announce trial start, a near-expiry warning and the outcome rather than speaking the countdown every second. Maintain at least Shelllist’s 42 px control target and support reduced motion.

Failure and lifecycle states are first-class UI

StateRequired behavior
Laptop only / no externalShow a meaningful single-screen summary. Keep the docking preference editable when supported: “Applies when an external display is connected.” Do not show enabled Mirror/External-only shortcuts.
Desktop, no internal panelKeep arrangement and output settings. Hide the laptop preference. Backend still prevents disabling the last usable output.
Integration off / service unavailableExplain the opt-in or connection problem. No synthetic “saved” state. Disable unsupported mutations; only show cached/read-only data with an explicit stale label.
Dock settling / hotplug during editingShow “Waiting for external display to stabilize.” Mark a topology-mismatched draft stale; preserve it for inspection, block Preview and offer Reload. Do not refresh over active typing.
Unplug or host disappears during trialRequest revert where possible, invalidate confirmation against the changed topology, and relocate confirmation/status to a surviving output. Backend fallback and durable recovery continue independently.
Restart, resume, connection lossResubscribe to a complete snapshot. Reattach to a reported trial or show its recovered result. Never replay an old mutation. Resume handling stays daemon-owned.
Policy conflicts / DPMS / lidFreeze policy changes while the local layout draft is dirty or a trial is active. Test concurrent clients; add backend conflict rejection where needed. Idle DPMS-off is not unplugging; display settings must not wake outputs or rewrite lid/sleep policy.
Unsupported saved mode / rollback failureShow the failing output and actionable reason; retain safe fallback and the recovery journal. Offer refresh/corrected preview only when safe; never report “restored” merely because the timer expired.
05 / DELIVERY PLAN

Extract first. Improve second. Extend deliberately.

No new display daemon is needed. Keep bar-daemon → bar-api → Displays controller → views as the ownership chain. QML presents and dispatches; Rust validates, journals, applies and reconciles.

PHASE 1
Independent surface

Move the existing capability without weakening it.

  • Add displays/ with a controller, backend/API adapter, flow reducer, content, policy pane, initial layout pane and qmldir. Extract display-specific pending/error state from Battery. Scope in-flight operations to the display domain.
  • Register a lazy-loaded, warm displays bundle in SurfaceRegistry.qml. Replace its redirect to Battery; keep existing IPC, CLI and global-shortcut entry points compatible.
  • Add the bar entry through the TypeScript source typescript/bar/BarStatusPresentation.ts and bar/BarController.qml; regenerate JS using the project build tooling. Supply cheap shared display summary state without loading Battery.
  • Remove the two display cards and display subscriptions/handlers from Battery after cutover. Leave a small migration link in Power & sleep.
  • Update package copying/import paths, CLI help and direct-surface validation in flake.nix; add the module to QML test/smoke roots and contract checks.

Exit gate: all existing display actions and recovery tests pass through the new surface; Battery no longer owns display state or gates display operations.

PHASE 2
Recommended UI

Ship A plus the expanded B editor.

  • Build a compact current-state map, output rows, Identify overlays and the explicit persistent-policy switch. Add optional display description/manufacturer/model metadata to the daemon snapshot for friendly names; fall back to connector names.
  • Add a pure layout/draft model: transformed logical rectangles, stable selection, edge snapping, relative placement, exact advertised modes, validation and dirty/stale tracking. The current internal-fallback draft must never masquerade as the actual enabled-screen summary.
  • Build the canvas and inspector on shared theme/control components. Use Ui.ScrollableListView for vertical output/result lists; preserve native touchpad and wheel scrolling.
  • Implement full keyboard focus traversal, screen-reader equivalents, adaptive width, confirmation/recovery status, and host relocation if the invoking output disappears.
  • Harden daemon conflict handling as required: policy writes during trials, topology changes before confirm, duplicate requests, and concurrent clients. Reuse the existing journal, deadlines and active-session checks.

Exit gate: keyboard-only editing is complete; no direct compositor mutation comes from QML; trial safety works even when the UI dies.

PHASE 3
Optional extensions

Add modes and profiles only with a coherent backend contract.

  • Introduce a capability-described, single transactional mode operation before offering “Laptop only / External only / Extend / Mirror” presets. It must define temporary versus persistent policy, stage both policy and layout, and roll both back together. Do not race separate displayPolicy.set and displayLayout.preview calls.
  • Mirroring needs an explicit source/target model, compatible mode/scale handling and error reporting. It is not represented in today’s layout payload. Exclude it from v1 rather than ship a decorative disabled control.
  • Named Home/Office/Presentation profiles need topology identities beyond connector strings, schema migration and ambiguous-identical-monitor handling. The current saved layout document is not a multi-profile engine.
  • If justified, add C through a DisplayProvider and the existing provider registry. Actions resolve capabilities at execution time and use the same controller/trial path, not a second settings stack.

Exit gate: new backend contracts and fixtures precede new UI affordances. Core display migration does not wait for profiles or mirroring.

Verification before enabling on real monitors

Automated / no physical output changes

  • Unit-test logical geometry at mixed scales, 90° rotation, negative coordinates, three outputs, snapping, exact mode round trips and non-finite input rejection.
  • QML-test independent open routing, no Battery initialization, stable keyboard focus, dirty-state preservation, disabled controls and the no-internal-panel case.
  • Extend tests/check-battery-controls.js / tests/qml/tst_battery_sleep.qml coverage into display-specific tests; update tests/check-bar-api-contract.sh and checked fixtures.
  • Use fake compositor/daemon tests for stale topology, wrong trial IDs, last-output protection, policy conflicts, client loss, clock jumps, restart/resume and failed rollback retry.
  • Run the existing QML test runner and nix flake check; assert generated assets/imports package correctly.

Manual / deliberate hardware checklist

  • Laptop alone; one external; two externals; desktop with no internal output; identical monitors through different dock ports.
  • Keyboard-only setup and recovery; 125–200% UI scale; a small logical viewport; light/dark theme and reduced motion.
  • Preview then Keep; Preview then Escape; let timeout expire; close/kill UI; restart daemon mid-trial; verify actual restored layout, not just UI text.
  • Unplug the selected or hosting output mid-trial; reconnect; dock flapping; lid close/open and suspend/resume with both policy values.
  • Unsupported modes and partial apply failure; ensure a usable output or recoverable fallback remains. Arrange a recovery path before risky tests.
Safety limit: compositor-visible “enabled” does not prove a human can see an image. GPU, cable and firmware failures cannot be solved by a callout. Preserve the fallback and journal, surface failures honestly, and never promise guaranteed recovery from hardware loss.

Acceptance: a user can find Displays without opening Power; understand which screens are active; change a layout entirely by keyboard; and recover from an unconfirmed change without relying on the UI staying alive.
