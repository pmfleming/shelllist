What does this app
actually cost?

Answer first. Explain second. Separate the space it occupies, the work it does, and the energy it consumes.

A proposal, not live telemetry.

Two complementary mockups, plus honest missing-data states. All numbers are illustrative; the idle example borrows selected values from your screenshot. No app or system settings are changed.

01Keep the shared timeline

Aligned lanes and consistent resource colors make events comparable. Keep them for investigation, but lead with answers instead of six mostly flat charts.

02Fix the categories

App data is not installation size. GPU allocation is not GPU activity. Referenced files may overlap app data. Full-width bars without a capacity denominator imply more than they say.

03Make the units do the work

Watts answer “how fast?”; watt-hours answer “how much?”. I/O needs both rates and period totals. “No measurements” must never look like measured zero, and confidence must stay next to estimates.

1

A qualified answer

Summarize what is actually known. Do not say “uses 6.1 MiB on disk” when the executable, libraries, or some data directories are missing.

Scope is part of the number
2

Temporary space gets its own line

Put persistent and temporary app data beside each other. The bar shows composition of identified data, not disk capacity or a severity score. “Temporary” does not imply safe to delete.

3

Capacity ≠ activity

RAM and GPU memory answer “how much is held?”. CPU and GPU percentages answer “how busy?”. Keep the two pairs together, but never sum RAM and GPU memory on shared-memory hardware.

4

Energy, not an opaque share

Show W now + mWh over a named period. A tiny nonzero reading should not round into an authoritative “0.00 W”. Keep low confidence and CPU-package scope visible.

5

Idle does not mean free

An app can be quiet now but have moved data earlier. Show read/write and receive/send separately, with totals below rates. No empty network graph masquerading as zero traffic.

No more “peak 75…”. Now, average and peak have separate positions. Average values are duration-weighted. Disk directions stay distinct.

7

Label each y-scale. An independently scaled CPU chart can reveal small spikes without implying the machine is maxed out. Retain common time boundaries.

8

Keep availability local

Network can be unavailable while disk is measured. If collection is interrupted, leave a visible gap and reduce time coverage. Never extend a last observation to “Now”.

Implementation boundary

Better presentation. Honest collection limits.

Reviewed against the existing QML resource view, TypeScript availability helpers, and resource contract fixture.

01 / Use the data already exposed

  • Disk data: disk_space_permanent_bytes, disk_space_temporary_bytes, and disk_space_total_bytes. Label the scope “identified app directories”. A current footprint is not a historical temporary-space peak.
  • RAM: memory_bytes with memory_source; expose swap separately. If the source is RSS fallback, label it instead of presenting it as PSS.
  • CPU / GPU: cpu_percent_of_machine and gpu_busy_percent. Keep resident versus allocated GPU memory explicit. Do not equate GPU time summed across engines with a bounded utilization percentage.
  • Disk / network I/O: use the respective byte-per-second fields. Preserve independent capability checks: network connections being available does not mean network bytes are available.
  • Energy: expose power, source and confidence together. An RAPL attribution is not a direct per-app whole-system power measurement; it does not include all display, GPU, disk, or network energy.

02 / Do not invent the missing totals

  • Installation footprint needs collection work. Resolve package-owned files, shared dependencies and actual allocated disk blocks. Deduplicate paths/inodes against app data. On Nix, distinguish exclusive storage from a shared store closure; neither is automatically reclaimable space.
  • Period I/O totals need defined semantics. Validate whether retained byte counters are interval deltas or cumulative counters before summing. Prefer reset-aware counter deltas. If integrating rates, label the result estimated and omit unobserved intervals.
  • Energy over the selected range: validate the scope of energy_mwh. Sum non-overlapping interval energies only if guaranteed; otherwise integrate attributed watts over valid durations and convert to mWh. Never multiply the latest watts by the entire range.
  • Memory I/O is still unmeasured. Logical file read/write counters may include cached file access; they are not DRAM bandwidth. Proper attribution needs a separate supported collector.
  • No additive “total resource use”. Bytes, percentages, rates and joules are different quantities. No green “efficient” badge without an explicit baseline and trustworthy coverage.

03 / Preserve the shared interaction model

  • The HTML buttons switch mock data only. Links navigate this document. They are not a proposed panel-specific keyboard workflow.
  • In Qt, keep ProviderChooserSurface / PanelSurface. Use the shared SegmentedControl for 30m / 2h / 24h. The fixed “Last 30 minutes” label here is not a working selector.
  • Tab visits editable fields only. Range edits save with Enter/Tab and discard with Escape; arrows edit natively. Read-only cards and charts do not become field stops. Keep power-history inspection pointer-only.
  • No invented primary action or “clear temporary files” command. If contextual actions are added later, use shared circular actions and Alt+letter commands with existing safety guards.

04 / Rollout and acceptance

  • First: regroup the overview, qualify storage, separate memory from activity, replace energy share with scoped power and period energy, and retain per-capability missing states.
  • Next: add well-defined range totals, metadata, and full-size chart statistics. Keep process-attribution coverage separate from time coverage and energy confidence.
  • Then: add installation/shared footprint attribution and temporary-space history. Show “not measured” until supported; do not ship guessed values.
  • When implementing Qt changes, add actual interaction tests for range save/discard and read-only field exclusion. Cover stale/retained data, zero versus missing, counter resets, partial windows, and narrow layouts. Follow docs/chooser-keyboard-workflow.md; update the contract for any approved interaction change.
Success criterion: In five seconds, a user can identify persistent and temporary disk use, live RAM and GPU memory, CPU and GPU activity, estimated energy over a named period, disk and network traffic—and which of those answers are incomplete.
