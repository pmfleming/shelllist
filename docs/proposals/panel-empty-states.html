Recommended / quiet identity + honest state

Same calm center. More precise meaning.

The shared list already supports a large emptyIcon. Bluetooth uses a blocked glyph when its radio is off or blocked; Notifications already uses a bell. Extend this pattern instead of building a different empty layout in each panel.

Important distinction: Bluetooth being disconnected does not make its device list empty. Known devices should remain visible. A slash means explicitly off or blocked—not “zero results”, “not paired”, or “no connection”.

Recommendation: icon-only center for ordinary chooser empty states; a short explanation in the existing status strip. Always give the state an accessible text name. Show visible text for failures, blockers, and section-level states that have no status strip. No oversized illustrations, fake rows, or permanent keyboard instructions.

Three rules for every panel

01 / Identity

Use the domain’s icon

Clipboard, monitor, speaker, calendar. Neutral foreground, roughly the same 64px footprint as Bluetooth. No filled circular button behind it: this is information, not an action.

02 / Progress

Animate the read, not the object

Keep the icon still. A small progress cue means a real pending read or scan. As soon as rows exist, remove the center icon; move progress to the header or paging footer.

03 / Scope

Replace only missing content

No battery history? Replace the chart, not Battery & Power. No forecast? Keep the city and clock. No todos? Keep the new-todo editor usable.

Resolve the state before choosing an icon

Keep usable content→ otherwiseKnown blocker / failure→Initial read pending→Settled no-match→Settled empty

State rules

  1. Content exists: retain valid rows, controls, charts, and the viewport. Refresh/append state is small and local. If old content is no longer trustworthy, use existing domain invalidation rules; never keep actionable ghost devices.
  2. Known unavailable/off/error: state the specific reason, even with zero results. A disconnected service is not a successful empty read. Keep retry/status recovery in the domain owner.
  3. No content + actual first read: domain glyph and a small progress cue. A proposed 200ms cue delay can avoid flash; do not delay focus or safety feedback. Bind to the read lifecycle, not a fabricated timer.
  4. Successful, settled search/filter zero: domain glyph + small search badge and “No matching …”. Resolve against the current query/category after debounce and pending reads; stale pages must not announce no matches.
  5. Successful, settled zero: bare domain glyph. If the underlying catalog is empty, prefer the real empty reason even if a search string remains.
  6. Collecting over time: a passive history mark and honest coverage text. “Collecting history” is not an in-flight request, a percentage, or a promise of completion.

Visual & accessibility specification

  • Placement: center within the result body, excluding header and status. Preserve height, clip, alignment, and details geometry. For inline cards, use a 32–40px mark with one short visible line.
  • Size/color: start at existing 64 × uiScale for list marks; use Theme.mutedText. Progress/search badge about 18–20px. No accent fill, focus ring, shadow, or placeholder hit area.
  • Text: icon-only center is recommended for routine emptiness. Expose the same localized reason accessibly and in the existing status strip. When an operation/screenshot owns that strip, show a short inline state label rather than replace its message.
  • Failures: keep visible reason and existing recovery, not just a red mark. Color is supplementary. A disconnected service uses an error badge; slashes are reserved for explicit disabled states.
  • Motion: animate only a small read cue. Stop when hidden, inactive, complete, or failed. Honor reduced motion with a static cue and unchanged text; no pulsing domain icon or skeleton shimmer.
  • Accessibility: one static-text state name; decorative mark/badge ignored by the accessibility tree. Use the existing announcement path where available; avoid per-row and per-frame announcements. Verify text contrast and visible glyph contrast on actual themes.
Implementation proposal / no panel-local variants

Build on the shared path that already exists

1. One passive presentation component

Propose Ui.ContentState (new name, not an existing API), reused by list bodies and section slots. Inputs: semantic icon, localized label, optional detail, read-pending cue, severity, and list/inline size. It paints only; it owns no backend calls, focus, shortcuts, retry, or selection.

Thread optional state properties through ChooserListPane → ChooserListBody → ResultListFrame, keeping emptyText/emptyIcon compatibility. Let Battery and Activity mount the same component inside missing-data sections under PanelSurface.

Important implementation trap: ResultListFrame currently assigns emptyIcon directly to text using the Nerd Font. Passing the string "content_paste" there would render a word, not a Material icon. The shared presenter must use GlyphLabel and explicit MaterialIcons mapping, while retaining legacy glyph support.

2. Domain adapters decide the truth

Each controller supplies enough facts to distinguish first-read readiness, successful empty content, current-query completion, availability, and ongoing reads. Use existing radio, snapshot, paging, and sync state; add explicit readiness only where genuinely missing.

Never equate generic busy or actionInFlight with list loading: they can mean screenshot capture, playback, pairing, preview, or a setting write. A shared rendering state must not become a second operation state machine.

Keep errors, pending acknowledgements, retry limits, portal/pairing modals, notification reply drafts, and display trial rollback under their current owners. Do not hide state merely because an unrelated request succeeded.

3. Reuse icon assets, not browser drawings

Baseline names already resolved by the icon layer include apps, bluetooth, wifi, content_paste, monitor, cloud, speaker, mic, music_note, battery_full, refresh, and error.

Register and check names needed for direct semantic use: search, history, calendar_month, checklist, notifications_none, and wifi_off. Some already resolve through legacy glyph aliases but not as direct names. Keep Bluetooth’s existing blocked glyph; widgets is an optional Tray differentiation, not a prerequisite.

The self-contained SVGs here are review illustrations only. Use packaged fonts/theme tokens in QML; no new runtime network assets.

4. Interaction stays exactly where it is

  • Keep ProviderChooserSurface/PanelSurface and their shared navigation. State marks are not result rows, editable fields, or Tab stops.
  • No automatic focus jump when the first row arrives. Preserve selection/viewport on later page fills. Let shared navigation handle a removed final result and unavailable details.
  • Enter saves, Escape discards, Tab saves and continues editing; arrows retain result/native-edit meanings. Status transitions must not commit drafts.
  • Retry/refresh remain existing commands with capability guards and Alt+letter/F5 routes where supported. No new center “Enable”, “Retry”, or “Add” button with its own key model.

Normative interaction model: chooser-keyboard-workflow.md. This proposal does not change it. During implementation, document the shared passive-state behavior and test coverage there.

Delivery plan

Small shared change, staged rollout

01 / foundation

Shared renderer + facts

Agree icon-only/list and inline/section variants. Add the passive renderer, icon mapping, and state tests. Audit read readiness and status ownership before wiring glyphs.

02 / list panels

Match Bluetooth first

Bluetooth and Notifications establish parity. Then Applications, Clipboard, Wi-Fi, Displays, and Time & Weather. Keep current operations and paging intact.

03 / system choosers

Specialize generic copy

Audio, Media, and Tray share one content implementation but need different identities and readiness sources. Do not make Tray wait for the audio/media backend.

04 / partial surfaces

Scope to sections

Agenda, Todos, forecast, battery history, and application resource history. Keep surrounding controls and valid data visible. Verify no-battery desktop behavior.

Required Qt interaction coverage

  • New tests/qml/tst_content_state.qml: empty/loading/error/no-match rendering, semantic and legacy glyphs, accessible label, no focus target, motion stopped when inactive.
  • Extend tst_chooser_keyboard.qml and tst_result_list_reactivation.qml: zero → first row → more rows → zero, real key delivery, no focus theft or stale details, stable expansion and selection.
  • Extend tst_clipboard_recovery.qml and tst_notifications.qml: first-page failure vs empty, stale-query suppression, append/refresh preserving viewport and active reply/editor draft.
  • Extend domain suites: tst_system_choosers.qml, tst_displays.qml, tst_wifi_operations.qml, tst_bluetooth_recovery.qml, and tst_domain_workflows.qml. Verify off vs no hardware vs disconnected, tray menu ownership, modal safety, retry guards, and partial data.
  • Run tests/run-qml-tests.sh and tests/run-qmllint.sh. Add focused section-state fixtures for battery/history/agenda if existing suites do not cover their real rendered controls.

Visual acceptance & done criteria

  • At zero rows, each chooser has a recognizable domain mark and a truthful, accessible reason. Query miss, off, absent hardware, and service failure are not visually conflated.
  • At one or more valid rows, no giant glyph obscures content. Loading-more stays at the footer; background refresh never blanks the list.
  • Check narrow/collapsed/expanded panels, 1×/1.25×/2× scaling, long localized reasons, dark/light palettes, and reduced motion. No overlap with header, status, or trial controls.
  • Validate a missing battery, paused player, muted output, DND, forecast-only outage, and no registered tray apps. None should turn useful content into a fake failure.
  • Native screen-reader acceptance confirms a meaningful state label, no spoken font ligatures, and no repetitive announcements. Offscreen tests alone are insufficient.
  • State-only changes dispatch zero backend writes and preserve all domain acknowledgement, validation, privacy, and recovery guards.
