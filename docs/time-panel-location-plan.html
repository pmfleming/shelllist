02 / Product model

Three roles. Never silently interchangeable.

Home · Amsterdam

One permanent reference city, with Europe/Amsterdam and validated Amsterdam coordinates. A house icon denotes Home. Its clock follows Dutch DST, not a fixed UTC offset.

Cannot be removed, reassigned or moved. While at home, show only Home: no second Current row, Current icon or Current metadata.

Current location

One durable location state, independently owned by policy. A target/crosshair icon denotes Current, distinct from the ordinary saved-city pin. Shows acknowledged place and Manual/Automatic provenance.

Cannot be removed. Its separate stable current-location row appears only with a usable acknowledged location away from Home. Unknown location never creates a blank placeholder. At home, suppress that row—not the underlying location state or its controls.

Saved cities

User-managed places for clocks and weather. Each has its own stable ID, display name, country/region, coordinates and IANA timezone.

Add/remove changes only this collection. Saving a city does not make it Current, and removing it does not undo a manual Current location.

Proposed interpretation to approve: “Set current location manually” chooses a place and its system timezone, pausing automatic movement until “Return to Automatic.” This matches the existing automatic authority and makes the top-bar clock agree after verified application. It does not change UTC time, NTP, Home or saved cities. A panel-only location override would be a different scope.

At home means the Amsterdam timezone

Requested rule: when the acknowledged effective location’s timezone is the same canonical IANA zone as Europe/Amsterdam, omit the separate Current location list item. This applies anywhere in that timezone, in both Manual and Automatic mode—not just Amsterdam’s city boundary.
  • At home: Amsterdam shows only its house icon and Home identity. Its fixed coordinates, map, forecast and saved ID stay Amsterdam’s. There is no Current icon, label, metadata or extra row; Manual/Automatic commands still operate on the underlying policy.
  • Away: Amsterdam retains its house icon; the separate Current row carries the target icon. Other saved cities keep their ordinary place pin. These glyphs are passive, not buttons or Tab stops, and do not add a command gutter.
  • Timezone identity, not offset: normalize recognized IANA aliases in the daemon. Equal UTC offsets or “CET/CEST” text alone are insufficient. A different canonical zone does not become Home merely because its clock currently agrees.
  • Unknown/pending: with no usable acknowledged effective location, omit Current rather than show a blank row; never invent a city or infer Home from the machine’s timezone alone. During acquisition retain the last effective state and its honest provenance; only an accepted new location changes row visibility.
  • Selection: if selected Current disappears on arrival home, select Home without changing the open tab/expansion; if Home is filtered out, retain the query and use the normal surviving-result fallback. On departure, reinsert current-location without stealing selection from Home or another city.
  • Scope: this suppression applies only to the special Current row. Never delete or hide a saved city merely because it shares Amsterdam’s timezone. Automatic and Manual commands remain available through every city header even when Current is suppressed.

03 / User journeys

Four deliberate actions

A / ADD A CITY · proposed Alt+A

Search → choose → Add

  1. Click the small plus in the existing search bar (or Alt+Enter / Alt+A), including when the list has no search matches. Open a compact shared required-input picker: one search field, candidate list and existing submit/cancel commands. No wizard or permanent settings form.
  2. Search a place catalog through the daemon. Results show city, region, country and timezone to distinguish ambiguous names.
  3. Select a candidate; preview its identity. Explicit Add saves it. Typing/highlighting performs reads only.
  4. After durable acknowledgement, show the saved row. Select it if the initiating view is still active and its query is unchanged; clear that filter only in this owned completion path to reveal the new row. Otherwise preserve the user's newer navigation.

Exact duplicate: return the existing saved/Home identity, not another row. Different cities in one timezone remain distinct. Adding Amsterdam resolves to the protected Home row.

A new saved city gets a clock immediately from local zone rules; forecast loading/failure does not roll back the addition. Cancel or close before submission writes nothing.

B / REMOVE A CITY · proposed Alt+D

Selected saved city → confirm → remove

  1. Click the small trash icon in the existing details header. Its command targets the selected saved-city ID; Alt+D / the shared command menu also works collapsed. Home/Current retain an unavailable icon, not a new explanatory row.
  2. Use shared ConfirmationDialog: “Remove Tokyo?” Cancel receives initial focus.
  3. Capture the ID and revision at opening. Revalidate permissions/existence at confirmation; never retarget after selection changes.
  4. Remove only after persistence is acknowledged. Select the next surviving result at the old position, or the previous one at the end; preserve expansion where valid.

Home and Current are not removable, even via direct API calls. Removing a saved city currently used manually leaves Current untouched: manual location stores an independent place snapshot.

Remove its saved weather/clock membership together, including legacy merged aliases, so another projection source cannot immediately recreate it. No claimed Undo without a real native restore operation.

C / MANUAL CURRENT · proposed Alt+L

Choose a place → Set current location

  1. Click the single filled target primary in any city’s existing details header, or Alt+L. Open the same compact picker titled Set current location manually, prefilled with the selected known place. Use saved cities/Home as candidates alongside catalog search; no separate tab or management screen.
  2. Show the selected place and timezone; disclose that this sets the system timezone and pauses automatic location.
  3. Explicit confirmation submits one authorized authority operation. It cancels/fences older automatic acquisition before applying the choice.
  4. Publish Manual with the chosen place only after the verified durable outcome. Network changes, panel closure and restarts retain it.

No separate Add is required; this does not create a saved city. Choosing Amsterdam manually still leaves Home unchanged. Choosing a different city in the same timezone still changes location and enters Manual mode.

Do not represent a user-chosen city centroid as measured accuracy. The bar continues to use observed timedated data, never optimistic UI state.

D / RETURN TO AUTOMATIC · proposed Alt+R

Clear override → acquire → accept

  1. Click the automatic-location/compass secondary below the primary in any city’s existing details header, including Home while the Current row is suppressed. Alt+R / the shared command menu remains reachable with details collapsed, no fix or no search matches. This is an explicit command, not a new mode switch, and is distinct from Refresh/F5.
  2. For an ordinary Manual override, explicit activation durably switches requested mode to Automatic and schedules the existing policy checks.
  3. Until a fresh acceptable result arrives, retain the last effective location and system timezone. Keep the existing subtitle concise (for example Dublin · last manual); expose requested Automatic mode and pending acquisition in the full accessible description and, if presented, existing shared feedback. Never label the retained place as a new automatic fix or add a permanent pending banner.
  4. Replace Current only after native acceptance. Never briefly restore an old automatic fix or fall back to Amsterdam.

Already Automatic: command unavailable/no-op. Offline, VPN, unavailable GeoClue or provider cooldowns may delay acquisition; this is not a reason to change Home or invent a location.

An unresolved timezone write or external-administrator pause is a separate safety state. Use explicit acknowledgement/reconciliation before resume; ordinary resume must not silently clear an uncertain-write fence.

Shared interaction, unchanged. Main-panel Tab/Shift+Tab traverses editable fields only; arrows browse results or edit natively. Enter saves, Escape discards, Tab saves and continues. Commands use Alt+letter and stay outside field traversal. J/M/S remain reserved. City-picking dialogs use the existing required-input modal exception: contained conventional traversal and explicit submit/cancel. Underlying commands, refresh and tabs are blocked while the modal owns input.

Register commands through the existing shared surface host (additionalCommandItem / commandsWithoutDetails) and header composition, with one active registration per command. Add uses the existing search-action signal; Manual/Automatic are global intents despite their compact header placement, while Remove is selected-result-scoped. Do not add visible controls to the collapsed city rows or duplicate active shortcuts across layouts. Compose the picker from shared modal/search/list controls; any reusable missing composition belongs in qml/Shelllist/Ui/, with domain search/mutation ownership outside it.

Validation, authorization, uncertainty and retry guards remain mandatory regardless of presentation.

05 / Ownership & implementation

Two persistence owners, one timezone writer

Time & Weather UI
  └─ typed bar-api requests → session bar-daemon
       ├─ Saved-city catalog → durable user store → activity.changed
       └─ authorized control proxy → system bar-location-daemon
            ├─ Manual / Automatic policy + durable operation state
            └─ sole timedated writer → verified observation → timezone.changed

Native saved-city catalog

  • Add a versioned daemon-owned runtime store, separate from potentially read-only/Nix-managed activity.json. Use atomic durable writes and serialized revision-checked mutations.
  • Provide a protected weather:home identity for Amsterdam, retaining that existing ID where possible. Keep fixed place data in native product policy, not QML or forecast-provider defaults.
  • Import existing weather locations/world clocks once, preserving IDs and weather associations where possible. Map merged clock aliases to their saved record for removal. Do not deduplicate different geographic cities merely because they share a timezone.
  • If the old Home is not Amsterdam, preserve it as an ordinary saved city; install Amsterdam as Home. Back up/import transactionally; malformed input must not silently erase cities.
  • After migration the runtime catalog owns this list. Refresh must not reimport deleted config entries. Calendar-source config remains unchanged; later declarative city changes require an explicit import workflow, not an implicit merge.
  • Compute at_home natively from acknowledged effective-location zone identity, including alias normalization. Suppress Current entirely at home, including its icon and metadata; keep Home place data and underlying Current state separate. Publish at most one populated Current row away from Home. Never create an unknown-location placeholder.
  • Cache forecasts by stable city/config generation. Add fetches only the new place; remove cancels/drops that place's work and rejects late results without clearing unrelated caches.

System location authority

  • Add narrowly scoped Manual and Return-to-Automatic control methods, serialized with the existing acquisition/write state machine—not a parallel timezone writer.
  • Extend the private durable state and migration to represent explicit mode, manual place, effective provenance, control generation and recoverable operation identity. Keep accepted automatic evidence separate from user input.
  • Preserve GeoClue/IP confirmation, VPN blocking, freshness, sleep/network cancellation, canonical-zone comparison, cooldowns and uncertain-write protections for automatic acquisition.
  • Manual city selection does not need automatic provider agreement or internet when a saved candidate is available. It still requires valid coordinates/zone, authorization and native write verification.
  • Authorize every mutation on the system bus using the actual caller's session identity. The session proxy must not accept a client-supplied UID as authority. Specify active/local-session and multi-user policy explicitly.
  • Keep coordinates/place payloads out of world-readable status and ordinary logs. Extend authorized reads for mode/effective-place state; public revisions can trigger those reads.

08 / Scope decisions before coding

Recommended first release

Included

  • One search plus; the same Manual primary and Automatic/Remove secondaries for every city, without redesigning Time or Weather.
  • Permanent Amsterdam Home, enforced natively.
  • Distinct passive Home/Current icons; one Amsterdam Home row at home, without a Current item or icon.
  • City search, durable add/remove, protected role identities.
  • Manual Current place plus verified system timezone.
  • Explicit Return to Automatic with honest pending/last-known state.
  • Saved-city weather using the existing provider and caching rules.
  • Shared interactions, authorization, restart safety and actual Qt tests.

Not part of this change

  • Changing Home, arbitrary coordinate editing or map-based selection.
  • Changing system UTC time, NTP or calendar timezone policy.
  • Automatic reverse geocoding or new weather requests for Current.
  • Drag-to-reorder, city renaming, bulk removal or Undo.
  • A new navigation/key model, top toolbar, settings page, persistent management card, mode switch or city-row action gutter.
  • Changes to existing city sorting, weather artwork, map geometry or Time/Weather content composition.
  • Automatic deployment or live timezone changes without authorization.

Approval points: confirm that manual location should change the system timezone; that imported city configuration becomes daemon-managed after migration; and that online city search may use the selected geocoding service. The requested permanent Amsterdam Home is treated as fixed, not an open design question.
