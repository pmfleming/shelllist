Shelllist Wi-Fi Resize Artifact Findings

Summary

The blue rectangle seen after closing the options/details panel is most likely caused by a synchronization mismatch between the QML layout state and the outer Quickshell window size. The most promising fix is a shared animated width model: one width/progress value should drive both the outer window size and the internal details panel width.

Observed artifact

In ~/Downloads/15190.mp4, after the options/details panel is closed, a blue rectangular area remains visible on the right side and slowly collapses. This looks like stale or exposed compositor/window backing during a shrink transition, not like normal list-panel rendering.

Current code behavior

The current close path appears to allow the outer window target width and the details pane state to change at different times:

  • detailsWindowExpanded controls the current desired window width.
  • detailsOpen controls whether the details pane remains in the layout.
  • On close, detailsWindowExpanded is set false immediately.
  • detailsOpen may remain true briefly via the collapse timer.

That creates a temporary mismatch: the window is already trying to become narrow while the QML layout can still be in a wide/details-open state.

Quickshell documentation findings

  • For FloatingWindow / QsWindow, the desired size should be controlled using implicitWidth and implicitHeight.
  • Setting actual width / height is deprecated; the docs say to use implicit sizes instead.
  • The window color should remain set to the app background to avoid exposing a default white backing surface.
  • For PanelWindow, using anchors and margins for placement is correct. Opposite anchors force the corresponding dimension to screen size, so the existing top/left plus margins approach is appropriate for centered popover placement.

Hyprland documentation findings

  • Hyprland dispatchers can move or resize windows, but for this case Qt/Quickshell should own the size.
  • Compositor-side resize commands such as resizewindowpixel should be avoided for this UI transition.
  • Using Hyprland only for floating placement/recentering is reasonable.
  • hyprctl calls are synchronous, so repeated shell calls during animation should be avoided.
  • On Hyprland 0.55+, current config docs use Lua-style effects such as no_anim = true.
  • Layer-shell surfaces use layer rules matched by namespace, not normal window rules.

Why the no-animation rule may not be enough

Even if Hyprland animation is disabled, the artifact can still occur if the application itself commits inconsistent geometry: a narrow outer size while the inner layout still expects the wide details pane, or vice versa. Therefore the fix should not rely only on compositor animation rules.

Recommended solution: shared animated width

Introduce one conceptual expansion value and derive all geometry from it.

  • expansionProgress = 0: closed/list-only state.
  • expansionProgress = 1: fully open list + details state.
  • Window desired width = closed width plus progress times the open/closed delta.
  • Details pane width = derived from the same progress/window width.
  • Details pane stays loaded while progress is greater than zero.
  • Details state becomes fully closed only after progress reaches zero.

Placement recommendation

If visual centering during the animation is important, recenter the floating window as the shared width changes. However, avoid compositor-side resize dispatches. If live recentering causes jitter, prefer one final recenter after the width animation completes.

Alternative: delayed shrink

A simpler but less elegant fallback is to keep the outer window wide until the details pane has visually collapsed, then shrink the window. This reduces the chance of exposed backing surfaces, but the shared-width approach is cleaner because it removes the desynchronization at the source.

Conclusion

The likely root cause is not simply “Hyprland animations ignored”; it is a geometry ownership and timing problem. The most correct convention-compliant fix is to let Quickshell own the desired size through implicitWidth, and ensure both the outer window and inner panel are driven by one shared animated width/progress value.

Avoid a close sequence where the outer window width becomes closed immediately while the details pane remains open for a timer. That is the most suspicious current behavior.
